## 一、数据 / 下载

### 1. 自动下载 Spider / Olist 失败
- **现象**：`download_data.py` 里预置的下载链接全部 404；HuggingFace 连接超时（`timed out`），`raw.githubusercontent.com` DNS 失败；官方页 `yale-lily.github.io/spider` 也 404（托管地址已变）。
- **根因**：① 链接是凭印象写的，失效；② 本机/网络对部分域名的出口受限（GitHub raw、HF 被断，但 `github.com`、`pypi.org` 通）。
- **解决**：下载脚本改为**支持 `--url <直链>` 覆盖 + `--verify` 校验结构**，并明确提示"用浏览器手动下载 + 放到目标目录"。数据集改为**用户自己下载**，仓库只提供**导入器** `tools/build_olist_db.py` / `tools/download_data.py`（含目录结构校验）。
- **教训**：**评测脚本必须能在数据集缺失时"大声跳过"而不是静默失败或伪造数据**——这条后来被贯彻到 `eval_external_bank.py`（找不到 Spider 就明确报错退出码 2）和 CI（缺数据时跳过而非报红）。

### 2. Olist 导入报错：`unable to open database file`
- **根因**：输出目录 `data/olist/` 不存在，`sqlite3.connect` 无法建库。
- **解决**：`build()` 里先 `out.parent.mkdir(parents=True, exist_ok=True)`。

### 3. Olist 导入报错：`UNIQUE constraint failed: reviews.review_id`
- **现象**：orders/order_items/customers/products 都导入成功，唯独 reviews 报唯一约束冲突。
- **根因**：**Olist 真实数据的已知质量问题**——评论表 `review_id` 存在重复（100,000 行 / 99,173 个唯一值）。
- **解决**：`reviews` 表**去掉 `review_id` 主键**（保留为普通列）。
- **教训（这条后来真的救了评测）**：真实数据有脏值，**口径必须显式说明**。
  同一处的去重口径最终写进了配置的 `desc`（"评价数/好评率采用 `COUNT(DISTINCT review_id)`"），
  也成为修复"评价类指标被条目数加权"那类口径 bug 的前提。

## 二、评测方法学

### 4. `--limit` 语义错误（"没限住"）
- **现象**：以为 `--limit 50` 只跑 50 条，实际每个库都取前 50（20 库 × 50 ≈ 1000 条），等于没限。
- **根因**：limit 在"每库循环内"应用，而非全局。
- **解决 / 教训**：**抽样参数必须是全局语义**；并且"取前 N 条"不是抽样——
  现在 `eval_attribution_llm_baseline.py` 用的是**按 (维度×期×注入档) 分层 + 固定 seed 随机**，
  并在报告里写明"不是事后挑引擎表现好的时段"。**固定种子 → 抽样可复现**是硬要求。

### 5. "数据是真实的"不等于"基准是外部的"
- **问题**：项目早期所有命中率/准确率的分母都是**自己出的题**（Olist 域，问题与标签都由实现者定义），
  这在方法论上只是自证——数据真实解决不了"度量对象由被度量者定义"的问题。
- **解决**：接入**第三方定义**的语料：Spider dev（问题与 gold SQL 由数据集定义，对错由 gold 的执行结果裁定），
  并**明确标注**它属 dev 集、建层时看过题面，因此覆盖率是"开发集覆盖率"，不是泛化指标。
  可直接由代码/测试独立验证的主张（守恒、审计、密码学）继续用自测，**效果类主张必须有外部判官**。
- **教训**：区分「可由代码自证的性质」与「必须由外部裁定的事实」，是这类项目最容易含糊过去的地方。

## 三、架构定位

### 6. 业务数据"又捏造" / 项目像个验证 demo
- **问题**：最初业务层用"跨境电商/华东区/退款表/库存"配置，被指出"数据又是捏造的？"，而且臆造行业显得像玩具。
- **解决**：业务层改用**真实公开数据集 Olist（约 10 万订单）** + 通用业务指标（GMV/客单价/取消率/评分），
  用"业务词典 + 指标配置 + 权限/审计"把它包装成真实业务产品，而不是绑定某个臆造行业。

### 7. 删掉自由 SQL 生成引擎（本项目最重要的一次技术决策）
- **问题**：早期主线是"LLM 生成 SQL + 独立评审 + 报错自愈重试"。它多解了一些题，
  但失败模式不可接受：**口径漂移**（同一问题不同次生成口径不同）、**无法审计**（公式不在任何地方沉淀）、
  以及最危险的一种——**错误伪装成合理数字**（语法对、能跑通、结果错）。
- **解决**：整条链路（含 Writer/Critic 角色、`MAX_REPAIR_ROUND` 护栏、消融评测脚本）**整体删除**。
  现在的铁律是：**口径内**由配置 + 编译器确定性生成 SQL；**口径外明确拒绝**并给出可操作原因。
- **教训**：**删掉一个能加分的功能，比加上它更能说明判断力**。衡量标准不是"能答多少题"，
  而是"答错的时候会不会被用户看出来"。
- **这条决策的代价也被量化了**：语义层因此有明确覆盖边界（外部基准上目标形态覆盖率 58.3%），
  而边界是**可见的**——见 `evaluation/reports/external_bank_world_1.md` 的拒答归因表。

### 8. "LLM 不写公式，那 LLM 还写什么？"
- **问题**：业务模式里如果"先让 LLM 写公式、再用配置覆盖"，属白写 + 多余，逻辑矛盾。
- **解决**：把 LLM 的职责收缩到**识别意图**（自然语言 → 从**已登记**口径里选一个）与**把归因翻成人话**；
  SQL 一律由 `compiler.compile_spec` 从配置拼装，公式不在 LLM 手里。
- **一个必须堵上的口子**：LLM 猜出来的口径**不允许直接执行**——
  先落库一条**口径确认记录**（`confirm_id`），回显"系统猜的口径 + 官方候选清单"，
  用户确认或改选后才拉数；该记录**一次一用**（防重放），无效 id 直接拒绝而不回退成"照猜的执行"。

## 四、健壮性 / 网络

### 9. 单条 LLM 超时导致整个评测崩溃
- **现象**：跑批到一半 `The read operation timed out` → `RuntimeError`，整轮挂掉。
- **根因**：`_chat` 里一次超时即抛异常，且超时 120s / 重试 3 次，一次卡住可拖约 6 分钟，看起来像"卡死"。
- **解决**：① 单题失败**只标记该题失败，不中断整轮**；② `_chat` 加**指数退避**；
  ③ 把超时/重试调小（60s / 2 次），让卡住最多约 2 分钟即放弃，减少"假死"感。
- **沿用至今**：`eval_attribution_llm_baseline.py` 仍按这个原则写——单题 LLM 失败记为该题失败/弃权，
  绝不因为一次网络抖动让整批跑分作废。

### 10. 长任务"卡死"vs"慢"判断不清
- **现象**：需要多次 LLM 调用的跑批很慢，长时间没有新进度行，无法判断是在跑还是断了。
- **解决**：① **判据**——等 6–8 分钟看是否出现新进度行；出现=在跑，>10 分钟不动=真断网；
  ② 用**样本量**控时长；③ 超时调小。**"先定判据再决定要不要 Ctrl+C"**，而不是凭手感。

## 五、环境 / 工具

### 11. pip / 依赖安装被沙箱拦截
- **现象**：`pip install` 报 `Permission denied ... pip-unpack-*.whl`（沙箱限制子进程写临时目录）；部分包安装超时。
- **根因**：沙箱对子进程写盘的约束 + 网络耗时。
- **解决**：核心链路**只依赖标准库**（sqlite3 / urllib / dataclass / yaml），
  确定性部分无需重依赖即可运行与验证；LLM 客户端用标准库 urllib 直连 OpenAI 兼容端点（不依赖 langchain 重型 API）。
- **代价（一并说明）**：因此**前端构建无法在本机验证**（`npm run build` 需要 piped stdio，被沙箱拒绝）；
  `web/` 源码已入库，构建校验交给 CI 的 `web` job（`npm ci` + `npm run build`）在 push/PR 时执行。

### 12. 版本对齐（langgraph / langchain 1.x）
- **解决**：`requirements.txt` 对齐 `langgraph>=1.2.11 / langchain>=1.4.0 / langchain-openai>=1.6.0 / langchain-core>=1.6.1`；
  因 LLM 客户端自研、不依赖 langchain 重型 API，LangGraph 图只用稳定的 `StateGraph/START/END` API，升版不需改代码。

## 七、当前时代的三个真实案例（都能在仓库里复核）

### 15. 外部基准第一次跑，揪出 3 条错答
Spider dev `world_1` 首轮：覆盖 23 题、覆盖内正确率 20/23 = 87%、**错答 3 条**。三条各指向一个机制缺口：
| 现象 | 根因 | 修法 |
|---|---|---|
| `the Carribean`（题面自带拼写错）→ 返回**全球**面积（数值对、范围错） | 取值匹配失败 → 过滤器**静默丢失** | 新增"未知专有名词闸"：大写词组不在取值域内 → 拒答（按词组比对，避免误杀 `Central Africa`） |
| "shortest life expectancy" → 答成亚洲平均寿命 | 最值（argmax）语义表达不了，词形枚举还漏了 `shortest` | 最值词形集合写成**域配置项**，可审可扩 |
| "above the average population" 条件被忽略 | 比较类词形只认 `more than` | 比较词形入守卫，并改为**条件触发**（能表达则答、不能则拒） |
修完后 **错答 0**，并把覆盖率从 17.5% 提到 25.0%（目标形态 43.8% → 58.3%）——见
`evaluation/reports/external_bank_world_1.md`。

**教训**：**最危险的错不是"跑不通"，而是"结果看着合理、范围是错的"**。这类错只能靠外部判官发现。

### 16. 为了修外部基准，把自家功能改坏了
外部基准要求"district 过滤 → 用 city 表的指标"，于是加了"按支持度换指标"的消歧规则。
结果它**过度生效**：Olist 的 `每单件数按订单状态` 从"正确拒答"变成**静默改答成"商品件数按订单状态"**——
用户问 A 得到 B，而"指标识别准确率"这个聚合指标**依然是 100%**。
- **修法**：消歧**只允许在命中词长度相同的真并列候选之间**发生（长度不同意味着用户用词更具体，不许顶替）。
- **教训**：① **聚合指标看不出这种错**，必须逐条对比结果；② 修外部问题的改动要拿自家评测回归一遍。

### 17. 一个从未生效过的安全黑名单
外部对抗语料评测发现：`_BLOCKED_FUNCTIONS` **用小写函数名去匹配已经大写的 SQL**，
所以**这个黑名单从来没生效过**——`load_extension` 之前只是"恰好"被 SQLite 自身的扩展开关挡住。
- **修法**：修正大小写匹配，并补齐跨方言危险函数（`sleep / benchmark / load_file / pg_sleep / pg_read_file / dblink / xp_cmdshell` 等）。
- **教训**：**"看起来在防护"和"真的在防护"是两件事**。自测永远只覆盖自己想得到的场景；
  要用一份**来源与意图都显式标注**的外部语料去打，并同时度量**误杀率**（只看拦截率会掩盖误杀）。

## 通用经验

1. **推理归 LLM、计算归代码**：执行、打分、护栏、归因算术全部确定性；LLM 只做语义映射与讲解。
2. **配置化口径**：公式/JOIN/依赖表/支持维度全在配置；换一个完全无关的业务域只加了一个 YAML，**0 行业务代码**。
3. **宁可拒答，不可错答**：规格表达不了就显式拒绝并给可读原因。判别一个可信系统的标准是它的**失败模式**，
   不是它的上限。
4. **多 Agent 要有证据**：异构角色 + 真实交互 + 消融数据，否则就是堆砌；
   更要紧的是**敢删**——本项目删掉了整条自由生成 + 评审 + 自愈链路，因为它带来的是不可审计的正确率。
5. **诚实 > 完美**：把"没实现的、样本小的、代价高的"说清楚；发现旧数字不可复现就删掉，
   不留"结果还在、章节划掉"的中间状态。
