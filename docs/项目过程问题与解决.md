# 项目过程：遇到的问题与解决

> 记录本项目从零搭建过程中真实遇到并解决的问题。按"现象 → 根因 → 解决"写，强调**排查思路**而非罗列。

---

## 一、数据 / 下载

### 1. 自动下载 Spider / Olist 失败
- **现象**：`download_data.py` 里预置的下载链接全部 404；HuggingFace 连接超时（`timed out`），`raw.githubusercontent.com` DNS 失败；官方页 `yale-lily.github.io/spider` 也 404（托管地址已变）。
- **根因**：① 链接是我凭印象写的，失效；② 本机/网络对部分域名的出口受限（GitHub raw、HF 被断，但 `github.com`、`pypi.org` 通）。
- **解决**：把下载脚本改为**支持 `--url <直链>` 覆盖 + `--verify` 校验结构**，并明确提示"用浏览器手动下载 + 放到目标目录"。Spider/Olist 改为**用户自己下载**，我提供**导入器** `build_olist_db.py` / `download_data.py`（含目录结构校验）。

### 2. Olist 导入报错：`unable to open database file`
- **根因**：输出目录 `data/olist/` 不存在，`sqlite3.connect` 无法建库。
- **解决**：`build()` 里先 `out.parent.mkdir(parents=True, exist_ok=True)`。

### 3. Olist 导入报错：`UNIQUE constraint failed: reviews.review_id`
- **现象**：orders/order_items/customers/products 都导入成功，唯独 reviews 报唯一约束冲突。
- **根因**：**Olist 真实数据的已知质量问题** —— 评论表 `review_id` 存在重复。
- **解决**：`reviews` 表**去掉 `review_id` 主键**（保留为普通列）。这是"真实数据处理"的典型坑，也成了面试可讲的点。

## 二、评测 / 指标

### 4. `--limit` 语义错误（"没限住"）
- **现象**：以为 `--limit 50` 只跑 50 条，实际每个库都取前 50（20 库 × 50 ≈ 1000 条），等于没限。
- **根因**：limit 在"每库循环内"应用，而非全局。
- **解决**：改成**全局上限**（跨库打平后再截断），并新增 `--sample N`（**跨库分层随机**、`--seed` 可复现），更代表性。

### 5. `--sample` 是轮询不是随机
- **现象**：用户问"这是前 300 还是随机 300"——当时实现是"跨库轮询"，每库取前面几条，库内非随机、有偏。
- **解决**：改为**分层随机 + 固定 seed**（每库先 `rng.shuffle` 再轮询取满），既覆盖各库、又可复现。

### 6. 自愈消融只在"第 1 个库"跑（不公平）
- **现象**：`--ablation` 的 L0/L1/L3 只对 `ab_benchmark`（首个库）跑，不是整批样本 → 结论不可比。
- **根因**：原实现把消融绑在"第一个 benchmark"上。
- **解决**：重构为 `run_ablation_multi` + `agg_summaries`（按样本加权合并），**对同一批跨库样本对齐跑 L0/L1/L3**，并输出 simple/complex 分档。

### 7. `--ablation` 在 mini 分支没触发（提前 return）
- **现象**：`run_eval.py --dataset mini --ablation` 只跑主跑，没出消融。
- **根因**：mini 分支 `return 0` 早于消融代码。
- **解决**：把消融从"真实分支末尾"抽成可独立调用的函数，mini/真实都触发。

## 三、多Agent 架构 / 定位

### 8. "多agent在哪？" 看不见 / 会不会显得生硬
- **问题**：用户质疑"我的多agent，多在哪？怎么体现？" —— 原实现把各角色写成一个 Python 函数，`agent_trace` 只是字符串，看似"一条流水线"；而"并行 N 个写手"本质是 best-of-N 采样（**单agent技巧**），硬叫N个agent会生硬。
- **解决**：
  1. 让每个角色**显式命名**（Router/Supervisor/SQLWriter/**Review**/Diagnose/Validator），`agent_trace` 记录"谁·角色·做了什么·耗时"，UI 里渲染成**多agent编排表**。
  2. 把"多"落在**异构角色 + 真实交互**上：核心是 **Writer↔Critic(评审者)闭环**（生成→独立评审→按意见修订→再审），而非"复制 N 个写手"。
  3. **消融框架已实现**：`--critic-ablation` 可在同一批样本上对比 单Writer vs Writer+Critic 的 EX。**注：本文档早期引用的"complex +3.6pp"等具体数值已移除** —— 仓库内无可复现的逐题产物，且 `data/benchmark_results.json` 对同一配置给出过互相矛盾的两组数，故不再引用任何准确率数字（详见 README「评测框架」一节）。

### 9. "LLM 写公式不算数，那还写干嘛？"
- **问题**：业务模式如果"先让 LLM 写公式、再用配置覆盖"，属"白写 + 多余"，逻辑矛盾。
- **解决**：改为**注入 + 校验**——业务层把**权威公式作为硬约束喂给 Writer**（LLM 不得改动，只负责搭询结构），再 `verify_formula` 校验"生成的 SQL 仍按配置公式"。LLM 写的是结构（用的上），业务层锁的是公式（兜底），**无冗余**。

### 10. 业务数据"又捏造" / 项目像个验证 demo
- **问题**：最初业务层用"跨境电商/华东区/退款表/库存"配置，但**为了贴合我就把真实业务落地、且要真实数据**，用户指出"数据又是捏造的？"。且"跨境电商"不是用户目标领域，显得像玩具。
- **解决**：业务层**改用真实公开数据集 Olist（~10万订单）** + 通用业务指标（GMV/客单价/取消率/评分），并通过"业务词典+指标配置+权限/审计"把它包装成**真实业务产品**，而非绑定某个臆造行业。

## 四、前端(Streamlit)

### 11. `st.dataframe` 报 `unexpected keyword argument 'columns'`
- **现象**：点运行后"执行结果"区报错。
- **根因**：新版 Streamlit `st.dataframe` **不再接受 `columns=` 参数**；且 `use_container_width` 已弃用。
- **解决**：改用"列名+行 → dict 列表"传给 `st.dataframe`；去掉 `use_container_width`（默认拉伸）。并按 `developing-with-streamlit` skill 的规范（宽用 `width="stretch"`、材料图标、`st.cache_resource`）。

### 12. `load_json_benchmark` NameError
- **现象**：`_engine_mode` 里 `NameError: name 'load_json_benchmark' is not defined`。
- **根因**：它只在 `_engine_data()` 函数内部 import，`_engine_mode` 里没引入。
- **解决**：在 `_engine_mode` 的 import 块补上。

## 五、健壮性 / 网络

### 13. 单条 LLM 超时导致整个评测崩溃
- **现象**：`--critic-ablation` 跑到一半 `The read operation timed out` → `RuntimeError: LLM 调用失败`，整轮挂掉。
- **根因**：`_chat` 里一次超时即抛异常，且超时 120s/重试 3 次，一次卡住可拖 ~6 分钟，像"卡死"。
- **解决**：
  1. `run_question` 里**捕获生成/评审阶段的 LLM 异常** → 标记该题 `llm_error`，**不中断整轮**；
  2. `_chat` 加**指数退避**；后续把超时/重试**调小（60s / 2 次）**，让卡住最多 ~2 分钟即放弃，减少"假死"感。

### 14. 长评测"卡死"vs"慢"判断不清
- **现象**：`Writer+Critic` 臂每条要多 1-2 次 LLM 调用（写手+评审+可能修订），100 条 ≈ 几百次调用，又慢又易超时，长时间无新进度行。
- **解决**：① 判据——等 6-8 分钟看是否出现新进度行；出现=在跑（超时后自愈继续），>10 分钟不动=真断网，Ctrl+C；② **降低样本量**（`--sample 50`）控时长；③ 超时调小；④ 可选"Critic 只在 complex 题介入"砍半调用。

## 六、环境 / 工具

### 15. pip / 依赖安装被沙箱拦截
- **现象**：`pip install pypdf` 报 `Permission denied ... pip-unpack-*.whl`（沙箱限制子进程写临时目录）；`pip install langgraph` 超时。
- **根因**：沙箱对子进程写盘的约束 + 网络耗时。
- **解决**：核心**只依赖标准库**（sqlite3 / urllib / dataclass / yaml），确定性部分**无需重依赖**即可运行/验证；LLM 客户端用标准库 urllib 直连 OpenAI 兼容端点（不依赖 langchain 重型 API）；`requirements.txt` 的 langgraph 等列为**生产版可选依赖**。

### 16. 版本对齐（langgraph/langchain 1.x）
- **现象**：要求升级到最新（langgraph 1.2.11 等）。
- **解决**：`requirements.txt` 对齐 `langgraph>=1.2.11 / langchain>=1.4.0 / langchain-openai>=1.6.0 / langchain-core>=1.6.1`；因 LLM 客户端自研、不依赖 langchain 重型 API，LangGraph 图用稳定的 `StateGraph/START/END` API，升版不需改代码。

## 七、诚实与可信度（最值得写进简历的一类）

### 17. 文档陈述与实现不一致（会被面试官戳破）
- **问题**：文档写了"并行候选 / LangGraph作为引擎 / 长时记忆(Chroma) / 断点续跑 / Schema-Linker裁剪"，但实际运行引擎是确定性编排器 `pipeline.py`，上述多为**未实现或仅参考**。
- **解决**：README **改为与代码口径一致**，把未实现项明确标注（"并行候选当前为顺序、非真并行""Chroma/Checkpoint 未实现""LangGraph 为参考图未接入"）。**诚实地披露"什么做了、什么没做"**。

### 18. 数据/指标口径写不准会被质疑"刷分"
- **问题**：业务样例 vs 基准易混淆；且项目早期曾出现"EX=0.81 / 0.86 / 0.88 等多个数字指向同一实验"的混乱（见 README「评测框架」一节对 `data/benchmark_results.json` 矛盾数值的说明）。
- **解决**：README 明确**两种模式隔离**（评测模式仅 Spider-dev；业务模式仅 Olist 演示，业务样例不算 EX）；并且**在拿到可复现的逐题产物前不引用任何准确率数字**。以往"标注 N、seed、噪声即可"的做法并不够——数字本身不可复现时，标注得再细也没有意义。

## 通用经验（可提炼给面试）
1. **推理归 LLM、计算归代码**：执行/打分/护栏用确定性代码，LLM 只做语义理解——这是防幻觉、防算错的核心设计。
2. **配置化业务口径**：指标公式写死在配置，LLM 只能"识别意图"+"搭结构"，不能改公式 → 解决"口径幻觉"。
3. **多agent要有"证据"**：异构角色 + 真实交互(生成↔评审) + **消融数据**证明，否则就是堆砌。
4. **评审者(Critic)不是越多越好**：设计上按需介入（简单题可关闭评审）以在准确率与延迟之间平衡。**具体增量数值不再引用**（原引用的 complex +3.6pp / simple 0 / 延迟 +33% 无逐题产物支撑，已移除）。
5. **诚实 > 完美**：把"没实现的、样本小的、代价高的"都说清楚，面试反而加分。

## 八、Case Study：从"报错"到"自愈"的真实链路

**问题**（跨表聚合）：`订单金额超过3000的客户名称`
**目标 SQL**：`SELECT DISTINCT c.name FROM customers c JOIN orders o ON c.cust_id=o.cust_id WHERE o.amount>3000`

本仓库（确定性编排器 + Mock LLM 触发一次真实 SQLite 报错）实际跑出的链路：

```
route=complex (2 tables, logic=False)          # schema 感知路由：跨表 → 走多Agent全链路
attempt1: ok=False err=sqlite: no such table: customer   # 首次生成的关键字错误(表名 a priori 错)
repair1:  [mock-diagnose] 疑似 no such table; 建议修正列名/别名后重试
attempt2: ok=True err=None                      # 修复后执行成功
```

- **修复次数 = 1，总尝试 = 2，最终有效 = True，退出原因 = ok**
- **max_repair 护栏**：当持续失败时，`repairs` 达到配置项 `pipeline.max_repair_round`（`config/settings.yaml`，当前值 **3**）判为 `max_retry` 终止，杜绝死循环（已单测验证）。
- **沙箱**：上述错误 SQL 中若混入 `DROP/INSERT/DDL/多语句/load_extension` 会被直接拦截（`tests/test_sandbox.py` 中 6 条恶意样本全部拦截，已测）。

> 这个 Case Study 的价值：**执行-报错-诊断-修复的闭环是真实发生的**，且安全与终止是确定性护栏，不依赖 LLM 自觉——这正是"不是理论假设"的直观证据。
