**怎么读这张表**（避免把数字读成"好看的假数据"）：

- 第 4 条的 53.6% 是**注入式真因**下的 top-1 定位命中率：在真实库上注入可控原因、由评测侧独立复算真值，
  不是"自己出题自己判卷"；top-3 到 **92.9%**，说明主因基本在前三名内，只是排序没排到第一。
- 第 4 条 drill **62.5%**（top-3 83.3%）：下钻注入从 60% 提到 **90% 专用档**（与 analyze 的注入比解耦，
  见 `--drill-inject-pcts`），下钻考的是"能否定位到**支配性子主因**"，弱注入会让靶点本就不是真值第一、
  从而**低估引擎**。剩下未到 top-1 的题属构造难度（靶点上月无销售→砍后仍为正 delta，或小州自然波动更大）；
  两项独立证据标明**不是引擎排序错**：① 引擎给注入品类的名次与独立真值**逐题一致（24/24 = 100%）**；
  ② "注入靶点确已成为该州内真值第一"的 15 题，引擎 top-1 **全中（15/15 = 100%）**。
- 第 3 条 80.0% 是**离线规则基线**（不接 LLM 时判断题判不出）；接真实 LLM 的值另有 `decisions_llm.json`
  （50 条集实测 **90.0%**，`llm_value = +10.0pt`）。
- 第 5 条分两段：段 A（真实数据、无真值）报"告警量的下降与成因结构"；段 B 用**注入式构造真值**
  （真异常=整期缩放价格/取消部分订单；真正常=缩放使日均持平、总值只剩月长差）给出真 FP/FN ——
  **阈值-only 假阳性率 66.7% → 统计门控后 0%、召回仍 100%**。是**构造分布**下的值，不等于真实流量分布。
- 第 6 条的 4.3% 只读误杀是"`SELECT 'DROP TABLE x' AS note` 这类字面量被拦"，属于**已知的保守代价**，已固定在测试里。
- 第 7 条 25.0% 是**开发集覆盖率**（`world_1` 属 dev 集，建层时看过题面），**不冒充泛化指标**；
  真正与"是否看过题面"无关的是"覆盖内执行正确率 100%"与"敢答且答错 = 0"。
- 第 8 条是**可选 LLM 对照**（`run_all.py --llm`，需 Key）：给纯 LLM 一个与引擎**信息对等**的分段表后，
  两者**逐题同答案**（当前仓库产物为单档 60% 口径 N=28，各 15/28 = 53.6%，一致率 100%；三档全量口径 74/74 亦然）。
  **所以引擎的价值不是"比 LLM 准"，而是可复现 / 零 token / 永不弃权 / 每个数字可追溯**。

> **注意读数字时的两个口径别混**：批量套件 `run_all.py` 为了跑得快，用的是**单档注入**
> （inject 60%、3 期 × 2 维 → 60 条注入 / 28 条有效），得到 top-1 **53.6%**；
> 而 `evaluation/reports/attribution_full.md` 是**三档注入比**的全量跑（180 条注入 / 74 条有效），
> top-1 **33.8%**。两者只差 analyze 的注入档与分母，**不是互相矛盾**，引用时请连同配置一起引。
> 下钻（drill）不受此影响：它用**独立专用档 `--drill-inject-pcts`（默认 90%）**，无论单档还是三档跑
> 都是同一批 24 条题、同一注入强度 —— 因此 drill 的 **62.5%** 口径唯一、可直接引。

## 产品指标（北极星：语义层命中率）

> 这一节回答"**这个产品到底覆盖了多少业务问题**"，而不是"SQL 写得对不对"。
> 跑法：`python evaluation/eval_product.py`，逐题明细落 `evaluation/reports/product.json`。
> 题集：`evaluation/business_questions.jsonl`——**88 条人工标注的真实感业务问题**（含 22 条新增长尾/口语化问法）。

| 指标 | 结果 | 含义 |
|---|---|---|
| ★ **语义层命中率** | **81.8% (72/88)** | 业务问题落到**已治理口径**的比例（主路径覆盖率，决定"口径一致"能覆盖多大面） |
| 口径内执行成功率 | **96.0%** | 命中的问题都真的跑出了结果 |
| 指标识别准确率 | **96.0%** | 识别出的指标与人工标注一致 |
| 维度识别准确率 | **98.7%** | 识别出的分组维度与标注一致 |
| 拒绝判定准确率 | **100%** | 指标支持但维度组合不合法时，**明确拒绝**而非硬生成 |
| 口径认证率（成功中） | **100%** | 返回成功的结果全部带"口径已认证" |
| 口径外拒绝占比 | **9.1% (8/88)** | 语义层没有对应口径 → **明确拒绝**（不是降级生成） |

**这些数字说明什么**：语义层已能覆盖大部分典型问法（24 个指标、4 档时间粒度、3 个派生指标）。
新增 22 条**长尾/口语化问法**后，命中率从旧 66 条题的 84.9% 回落到 **81.8%**——这正是把题集
从"教科书式问法"换向"真实口语分布"的效果。未落入口径的 16 条里：**8 条是语义层确实没有的口径**
（复购周期、LTV、利润等 → 待建口径清单）、**5 条是"指标命中但维度组合不受支持"的正确拒绝**
（拒绝判定准确率 100%）、**3 条是长尾口语句式在确定性关键词层的弱点**（"有没有 / 是不是" 里的
否定词被守卫拦下 → 待补句式清单）。它们**都不是"降级路径的用武之地"**（本项目不存在降级生成
未认证 SQL 的路径）。其中那 3 条句式弱点正是 `--llm` 对照要回收的对象。

> ✅ **「各品类的评分」采用订单粒度预聚合派生表**：reviews × order_items 是 1:多，
> 直接 JOIN 会得到**被条目数加权的错误均值**；改用派生表后，品维度下同一评价值重复多少次都不改变 AVG，
> 口径由 `desc` 写明。因此覆盖率 81.8% 里没有"错的命中"。

> ⚠️ **口径说明**：本评测**离线运行**（`llm=None`），走的是确定性关键词匹配链路；
> 因此这里的"命中率"衡量的是**关键词词表 + 口径配置的覆盖能力**。
> 线上有 LLM 时，未被关键词命中的问法会被 LLM 识别后**停在口径确认门**等人确认
> （`method=llm` 不允许直接执行，因此不产生未认证结果）。为量化这一层，本评测支持
> `python evaluation/eval_product.py --llm`：**只对离线未命中的口径内问题**补跑 LLM，
> 报告 `llm_path` 字段给出"口径内离线命中 → LLM 回收多少条 → LLM 识别口径率"的对照
> （度量的是"LLM 能否把长尾问法识别到正确口径"，不是端到端执行率）。
> 已实跑（`--llm`，模型 qwen3.8-27b）：口径内离线命中 72/75 → 回收 **1/3** 条未命中
> （`有没有哪个州的订单数特别少` 这类否定词句式由 LLM 正确识别）→ **LLM 识别口径率 97.3%**，
> 仅 3 次 LLM 调用。未提供 `--llm` 或缺少 API Key 时，`llm_path.enabled = false` 并如实
> 标注**未运行**；报告 `offline_note` 字段中同样记录了这一点。

## 多 Agent 决策质量（"下一步该往哪拆"值多少分）

> 这一节回答"**多 Agent 到底做了哪些判断、这些判断值多少准确率**"，而不是"能不能生成 SQL"。
> 跑法：`python -m evaluation.eval_decisions`（离线，零 token）；接真实模型加 `--llm`。
> 题集：`evaluation/eval_decisions.py` 内的 **50 条专家自标追问用例** = 40 正例（4 种动作均衡：drill 10 / switch_dim 9 / factorize 10 / none 11）+ **10 条判断题**（规则判不出、只等 LLM 真判断，衡量增值）。

| 指标 | 结果 | 含义 |
|---|---|---|
| **规则命中率** `rule_accuracy`（纯规则+门控，零 token） | **80.0% (40/50)** | 40 条正例由规则+门控确定性全中；10 条判断题规则判不出，离线只能蒙/漏 |
| **LLM 增值** `llm_value`（接 LLM 命中率 − 规则命中率） | **+10.0pt**（规则 80.0% → 接 LLM **90.0%**，qwen3.8-27b 单模型实跑） | 50 条集（40 正例 + 10 判断题）实跑：**判断题从规则 0/10 → LLM 5/10**，整体 `45/50 = 90.0%`；LLM 实际调用 **15 次**（其中 7 次落在规则判不出的判断题上）——见下方诚实口径 |
| **执行正确率**（做完算对） | **100% (4/4)** | 因子分摊守恒（`-70.000` vs `-70.000`）、份额合计 `0.9999`、主因方向正确、下钻分支内主因隔离 |
| 门控的价值 | **30/40 → 40/40**（仅正例） | 关掉策略门控还原旧规则即 30/40（10 条量价问法全漏），差值可被测试复现 |

**这套数字回答一类具体质疑**："决策层是不是还不如写死的规则？" 40 正例上，**旧**决策层（把 factorize 决定权整体交给 LLM）只有 30/40，
与规则打平——根因是 prompt 里一句指令级偏置（"若指标是 gmv…优先考虑 factorize"），导致 LLM 把"本月全国GMV是多少"也判成因子分解（过度应用 10 条）。
现在改成**代码管策略、LLM 管判断**：

1. **策略门控**（确定性，0 token）：`is_factor_question` 判定"这一问是不是在问量价"。只有放行才允许 `factorize`，放行后直接由规则给出。
2. **规则地板**（确定性，0 token）：没有追问语气 = 用户只是在看数/做对比 → 直接 `none`，不交给 LLM（实测 LLM 会"顺手多拆一层"）。
3. **LLM 判断**（花 token）：真实追问里"往哪儿拆、要不要换讲法"才交给 LLM；LLM 越界仍会回退规则并记 `gated_from`。

> ⚠️ **诚实口径（别把这些数字当成泛化准确率的证据）**：
> - **50 条真值（40 正例 + 10 判断题）由实现者自标**（依据模块内的判定规则），不是独立第三方标注，故只承担**回归测试**与**方法论演示**两个身份；系统级准确率只由公共基准 Spider-dev 支撑（其 gold 由数据源外部定义）。**关于"第二人独立标注"**：另一个人力标注全部 50 条并签署交叉一致性（如 Cohen's κ）在单人原型下客观不可得，故报告字段 `annotation_protocol.second_annotator = "unavailable"`、`agreement = null` **如实标注未做**，不虚构一致性数字；一旦有第二标注人回填即可升级。
> - 题集规模小，**任何命中率都不等于泛化**；门控判据本身是在观察这批问法后定的，存在过拟合风险（用"额外两条规则判不出、LLM 判得出"的用例做了反向校验，见 `tests/test_attribution_decisions.py`）。
> - 已实跑 `eval_decisions.py --llm`（qwen3.8-27b 单模型钉死，`--model` 不放开模型池）：50 条集实测 **规则 80.0% → 接 LLM 90.0%（`llm_value = +0.10`）**，
>   LLM 实际调用 **15 次**（其中 7 次落在规则判不出的判断题上），判断题命中 **0/10 → 5/10**；逐条 `source`（rule / llm）与判定明细见 `decisions_llm.json`。
>   **结论是"LLM 的判断力在规则判不出的那批题上确实有增量（+10pt），同时确定性门控仍省下了 35/50 次调用"**——不是"LLM 万能"，也不是"LLM 没用"。
> - 评测喂给决策层的是**原始问句**，service 层（`service.answer` 第 269 行）与多 Agent 链（`apiroutes/analyze.py`）喂的同样是**原始问句**——两边口径已一致，并由回归测试 `test_decision_layer_eats_raw_question_like_service` 钉死（此前的"已知口径差"已消除）。

## 外部公开基准评测（Spider dev · world_1）——"别人的题、别人的答案"

> **为什么单列一节**：上面所有命中率/正确率的分母都是**本项目自编**的问题集，属自证。
> 这一节换成**第三方定义**的语料：问题与 gold SQL 来自公开学术基准 [Spider](https://yale-lily.github.io/spider)（Yale LILY），
> 答案对不对由 **gold SQL 的执行结果**裁定，不是本项目说了算。
> 跑法：`python evaluation/eval_external_bank.py`（需 Spider 数据集，仓库外资源，`--spider-root` 指定）；
> 仓库内置样本语料（`evaluation/spider_probe/`）可在任意机器离线重跑；
> 完整分析见 `evaluation/reports/external_bank_world_1.md`，逐题明细 `evaluation/reports/external_bank_world_1.json`。

| 指标 | 结果 |
|---|---|
| 语料 | Spider dev `db_id=world_1`，N=120（65 个不同 gold SQL） |
| 覆盖率（**开发集**口径） | **30/120 = 25.0%**；语义层目标形态（单聚合）上 **28/48 = 58.3%** |
| 覆盖内执行正确率 | **30/30 = 100%**（行多重集与 gold 完全一致；列数不同直接判错） |
| **敢答且答错** | **0** |
| 显式拒答 | 90/120 = 75.0%（超纲句式 39 / 无对应指标 29 / 并列多指标 7 / 多取值「与」语义 6 / 未知专有名词 5 / 口径未登记 2 / 跨指标组内筛选 2） |
| 换域成本 | 1 个 YAML（`config/semantic_world.yaml`）+ **0 行业务代码** |

> ⚠️ **口径声明（必须连同数字一起引用）**：
> - **`world_1` 属 Spider 的 dev 集，建语义层时看过题面** → 25.0% 是**开发集覆盖率，不是 held-out 泛化指标**。
>   **覆盖内执行正确率不受影响**（看过了也不等于答对，判对判错由 gold 结果决定）。真正的 held-out 数字需要 Spider 未公开的 test gold。
> - **这不是通用 NL2SQL 系统**：规格只有 `{指标 + 维度 + 过滤(带算子) + 组内筛选}`，一次编译一个度量。
>   42/120 是"列出国家名字"这类**明细/取最大者**问题，指标层本就不该回答；把 N=120 当唯一分母并不公平。
> - **拒答率高是设计选择**：它的失败模式是"明确拒答 + 可读原因"，不是"给一个看起来很合理的数"。
> - 单库单域（3 张表）、有效样本量 65，规模小。

**表达力与守卫（评测反哺系统的固化结果）**：

- **守卫**：未知专有名词（大写词组不在取值域内 → **拒答**，按词组比对以避免误杀 `Central Africa`；
  取值域优先级按配置声明顺序）、最值词形集合（`unsupported_patterns`，可审可扩）、
  比较类词形（`above/below/at least` 等）；"事实表消歧"仅在命中词同长的真并列候选下生效。
- **表达力**：`QuerySpec` 支持**集合（或）/ 数值比较 / 否定排除（自包含反连接子查询）/ 组内筛选（HAVING）**，
  覆盖率 **25.0%**（目标形态 **58.3%**），**错答始终为 0**。
- **安全模型不放松**：① 规格里只出现**算子名**，SQL 记号必须来自配置白名单 `filter_ops`/`metric_ops`
  （实测 `op="'; DROP TABLE singer; --"` 被编译期拒绝）；② 取值逐字面量转义；③ 模板不含 `{op}` 时不允许比较算子；
  ④ 子查询过滤模板必须是配置写的自包含 SQL；⑤ 守卫与表达力联动——**线索未被成功表达成过滤条件时才拒答**，
  表达不了时照旧 fail-closed。
- 测试：`tests/test_query_spec_expressiveness.py`（20 项，含算子白名单注入、反连接取补集、HAVING 端到端）。

## 沙箱外部对抗语料（SQL 注入 / 越权写入）

> 跑法：`python evaluation/eval_sandbox_external.py`（自带语料，离线可进 CI）；报告 `evaluation/reports/sandbox_external.md`。

| 指标 | 结果 |
|---|---|
| 危险语料拦截率（76 条：写入/DDL/多语句/危险函数 + Oracle/MSSQL/PG/MySQL 跨方言 + 编码/篡改绕过） | **76/76 = 100%**，无绕过 |
| **只读语料误杀率**（23 条，含 UNION/CTE/JOIN/注释/字面量里的高危词） | **1/23 = 4.3%**（`SELECT 'DROP TABLE x' AS note`），已固定在测试里 |
| 库不变性 | 跑完整个语料后库文件 sha256 与各表行数**一字未变** |
| 过滤值注入（走编译器 `render_filter`） | **5/5** 被当作字面量（单引号转义、无分号逃逸） |

> 语料来源诚实声明：`evaluation/sandbox_corpus/sqli_corpus.jsonl` 是**按公开类别**（OWASP WSTG / CWE-89 / sqlmap tamper / 各库官方文档）**构造**的，
> 不是官方语料文件；`tools/fetch_external_corpus.py` 可在有网机器上换成 sqlmap / PayloadsAllTheThings 原始语料（记录 URL 与 sha256，抓取失败拒绝编造）。
> **不能**证明"对所有注入免疫"：规则型黑名单存在绕过的理论空间，真正的底座是 `mode=ro` + `PRAGMA query_only=ON` + 单语句限制 + 超时（即使策略层被绕过也写不进库）。
>
> **跨方言说明**：语料含 Oracle（`EXECUTE IMMEDIATE`/`DBMS_LOCK.SLEEP`）、MSSQL（`xp_cmdshell`/`WAITFOR DELAY`/`sp_configure`）、
> PostgreSQL（`pg_read_file`/`pg_ls_dir`/`pg_sleep`/`dblink`/`COPY ... TO PROGRAM`）、MySQL（`INTO OUTFILE/DUMPFILE`/`LOAD_FILE`）
> 专属 payload，以及编码（宽字节/双重 URL/十六进制）与 tamper（`space2tab`/`space2comment`）绕过类别。
> 执行层当前是只读 SQLite，方言 payload 常"函数不存在"而执行失败，但**策略层 `_sanitize` 是方言无关的**，
> 同一套负面清单同样作用于 MySQL/PostgreSQL 连接器——本语料断言的是**策略层拦截**，即"换库时安全策略不失效"。
> 本次扩充还据此发现并补上了旧负面清单缺口：`pg_read_binary_file` / `lo_import` / `pg_stat_file`（旧清单只有 `pg_read_file`，
> 词边界匹配不到带中间词的同族函数）。

## 指标口径（EX / EM 等）

- **EX (Execution Accuracy)**：执行结果与金标准一致即判对，忽略写法差异（最贴合业务价值）。**金标准自身执行失败的题不计为正确**，并在汇总中单独报告 `gold_failed` 数量。
- **EM (Exact Match)**：与金标准 SQL 逐字匹配（较严，参考用）。
- **端到端延迟 / Token 消耗 / 估算成本**：工程性能指标，随逐题产物一起输出。
