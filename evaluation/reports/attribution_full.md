# 归因命中率评测（真实 Olist 全量库 · 爆破式 100+ 用例）

> 本文为「口径在**真实数据**上跑过」的可复现证据。
> 关联 JSON：`evaluation/reports/attribution.json`（机器可读，与本文同一次运行）。

## 数据底座

| 项 | 值 |
|---|---|
| 数据库 | `data/olist/olist.db`（真实 Olist 全量库，`db_kind=full`） |
| 表规模 | orders 99,441 / order_items 112,650 / customers 99,441 / products 32,951 / reviews 100,000 |
| 评测入口 | `evaluation/eval_attribution.py`（默认 `--db` 解析到全量库） |
| 注入比档 | 30% / 45% / 60%（弱/中/强） | 期数 2018-05 / 06 / 07 | 维度 state / category |
| 靶点枚举 | 每(期×维)按当期 GMV 取 Top-10 段，跨期×维×注入比自动组合 |

## 玩法（为什么这次有统计意义）

不再是旧版的「每条维度只挑当期**第 1** 大分段、单一 60% 注入」那 6 条——
现在从真实库里**动态枚举**目标段（每期×维 Top-10 段），叠加**三档注入比**自动组合，
**共注入 180 条归因题 / 72 条下钻题 / 18 条因子题**。

每条仍是构造式真因（Ground Truth by Construction）：在真实库的**临时副本**上
对指定「期×维度×段」`UPDATE price` 制造扰动，再回收。

**命中判据（本轮修正）**：排名来自评测侧**独立 SQL 复算的 delta 真值表**（两期并集、缺失记 0、
与被测 gmv 同口径），**不读被测引擎的输出**；top-k、方向错、维度误报全部基于它。
同时报告"引擎自算的 delta 表 vs 真值表"的**一致率**（把"引擎算术对不对"变成独立可查的量）。

复现命令：`python evaluation/eval_attribution.py --report-dir evaluation/reports`（需全量库；
283 次 63MB 副本拷贝、约 18GB I/O，耗时十几分钟量级，故不进 CI）。

## 结果

### 1) 归因（analyze）命中率

> **命中判定的尺子**：由评测侧**独立 SQL 复算的 delta 真值表**给出排名（`truth_basis`），
> 不读被测引擎自己算的 `result["dims"][dim]["delta"]`。
> 旧实现读的是引擎的自报排名，实测连"delta 表里只放注入段"的假引擎都会被判 rank=1/命中 ——
> 也就是说该评测**发现不了引擎算错**（见 `tests/test_attribution_eval_truth.py` 的变异测试）。

| 指标 | 数值 |
|---|---|
| 总注入 | 180 |
| 有效题（判异常可归因） | **74**（106 题注入后总体仍 <5% 阈值，系统正确地不归因，N/A） |
| **top-1 命中率（独立真值表）** | **25/74 = 33.8%**（随机基线 ≈2.2%） |
| top-2 / top-3 / top-5 | 66.2% / **86.5%** / **91.9%** |
| 同口径**全量分母**（N/A 计入） | 25/180 = **13.9%**，N/A 率 **58.9%** |
| **方向错** | **0/25**（分母是 rank-1 的题数，不是 74 —— 只有排到第一才谈得上方向错） |
| 维度误报（rank-1 却属另一维更大） | 8/25 = **32%**（这是本表里最难看的一个数，如实保留） |
| 对照·引擎自评口径 | 25/74 = 33.8%（与真值口径相同） |
| **算术一致性**：引擎 delta 表 vs 独立真值表 | **74/74 = 100%**，最大绝对差 **0.0** |

**算术一致性为什么重要**：它把"引擎算得对不对"变成可证伪的一件事。实测 100% 一致 →
本轮改造前那批 top-1 数字在**算术上是可信的**；但当时它们**不可证伪**（尺子就是被测对象），
现在有了独立尺子，任何算术回归都会被立刻发现。

**分注入比（有效题 top-1）**：30%→18.2% · 45%→25.0% · 60%→**53.6%**。
（段数均值≈45.5，top-3 随机基线只有 3/45≈6.7%，实测 86%——远超随机说明系统**可靠地把注入因收进前几大贡献**；只有注入段恰好是全局第一大时才谈得上 top-1 精确命中。）

### 2) 下钻（drill）命中率

| k | 命中率 |
|---|---|
| top-1 | 20.8% |
| top-2 | 38.9% |
| top-3 | 47.2% |
| top-5 | 54.2% |

下钻比归因更难：注入目标是「某州内当期 GMV 第一大品类」，但该品类可能正处于自然上涨
（注入前 delta 为正），或同州另有**先前更大、当月塌方归零**的品类 |delta| 更大，
把注入目标挤到 top-2+。这是真实数据上「主因是否第一」的如实读数，不是定位失败。
（诊断实例：MG 2018-06 注入 `beleza_saude` 砍 60% 后 delta=-3016 已正确翻负，但同州
`automotivo` 天然塌 -6517，故下钻 top-1=`automotivo`，注入目标 rank=2。）

### 3) 因子分解（factorize）命中率

**18/18 = 100%**，且**独立实验数 18/18**（旧实现在量因注入上固定用 `--keep-frac`，
同一实验在 3 档注入比下重复跑 3 次 → 18 条里只有约 12 条独立；现在量因强度随档位变化）。

判定已加**优势门槛**：不仅要求 `main_factor` 正确，还要求**注入因子解释 ≥50% 的总变动**
（`share≥0.5`）—— 否则"注入即命中"只是 `max|contribution|` 的同义反复，不构成证据。
实测各题注入因子 share 在 0.82–1.03 之间，因此这条门槛并没有把结果"卡"出来。

### 4) 对照：确定性归因引擎 vs 纯 LLM（**修正后：信息对等，两者打平**）

> 对应 `evaluation/eval_attribution_llm_baseline.py`，产物 `reports/attribution_llm_baseline.json`。
> 复现命令：`python evaluation/eval_attribution_llm_baseline.py --limit 0 --seed 20260920 --topk-table 0 --model qwen3.8-27b`

⚠️ **本节此前给出的"引擎 54.5% vs 纯 LLM 18.2%"是稻草人对照，已推翻重做。** 旧实现有三处不公平：
① 喂给 LLM 的分段表只取**当期按体量 Top-12**，而引擎的 delta 表是**两期并集** ——
"当期塌成 0"的段对 LLM 直接不可见（而那恰恰是最典型的主因形态）；
② 表的 WHERE 带 `frag IS NOT NULL`、合计却不带 → 两臂分母不同；
③ prompt 只说"变动量"没点明"本月 − 上月"，且 22 条样本是**事后**从引擎表现最好的时段
（2018-05/06）取的。

修正后：分段表取**两期并集（缺失记 0）**、与合计**同一 WHERE**（表内合计 == 总合计，自校验 0 例不一致）、
prompt 明写"变动量 = 本月 − 上月"并提示"你可以做减法，不要只按体量判断"、
样本按 (维度×期×注入档) **分层 + 固定种子**抽全部 74 条有效题。

| 判据（top@1 = 命中的注入段，即真凶） | 确定性引擎 | 纯 LLM（信息对等） |
|---|---|---|
| 同 74 条 top@1 命中率 | **25/74 = 33.8%** | **25/74 = 33.8%** |
| 与引擎**答案完全一致** | — | **74/74 = 100%** |
| 弃权（`{"top":null}`） | 从不弃权 | **0**（旧版有 10/22 弃权，也是被 prompt 逼出来的） |

**结论（诚实且更值钱）**：**主因定位这件事 LLM 也能做**——给它同样的数据和一句明确的减法提示，
它与确定性引擎**逐题同答案**。因此引擎的价值**不是"比 LLM 准"**，而是：

- **可复现**：同一 spec 今天/明天给出逐字相同的 SQL 与排序，不随采样温度波动；
- **零 token**：主路径不花钱，覆盖率与成本不挂钩；
- **永不弃权**：确定性算术在每道题上都给出 top-1，不出现"无法确定"；
- **可审计**：每个结论都能指认到"哪条 SQL、哪个口径、谁负责"，而 LLM 的答案只能被信任、不能被复核。

这也正是本项目"生成链路零 LLM"红线的**真正论据**：红线是为了可审计，不是为了补模型的短板。

## 诚实注解（答辩必看）

1. **这是工程召回正确性，不是业务真因有效性**。"真因"是**人为注入**的
   （在真实库临时副本上对指定段 `UPDATE price` 制造扰动再回收）。命中证明的是：
   **引擎能找回我注入的点、按维度定位、并按注入方向判对**；它不回答
   "真实数据里的归因是否符合业务常识"——后者只能靠 `/api/analyze` 真实结论 + SP 人工复核逐条验证。

2. **top-1 不是 100% 是诚实而非缺陷**：爆破式多段枚举故意把**弱/中注入**灌进
   **未必是全局第一**的段（很多还在自然上涨）。注入段常常只是"该维第 2–3 大贡献"，
   top-1 精确命中率因此被稀释；但 top-3/top-5(86%/92%) vs 随机基线(2–7%)**显著超出**，
   且 0 方向错。换言之：系统「把注入口径当成前几大主因」是稳的，「恰好排第一」才受段本身地位影响。

3. **106/180 题判 N/A**：弱注入进小段时，整期 GMV 波动落回 <5% 健康阈值下面，
   系统**正确地不去归因**（`is_abnormal=False`）。这些**不进 33.8% 的分母**，但同一张表里给出
   **含 N/A 的全量分母 13.9%**（`hit_rate_all_injected`）与 N/A 率 58.9% ——
   因为"分母由系统自己的阈值决定"本身就是一个可被调参美化的口子，必须把两个口径一起报。

4. **方向错 0/25 而不是 0/74**：只有 rank-1 的题才有机会判错方向（25 题），
   拿 74 当分母是夸大。同理**维度误报 8/25 = 32%** 也如实列在表里 —— 这是本评测里最难看的一个数字：
   三分之一的 rank-1 题里，全局第一主因落在另一个维度上。

5. **执行安全**：`eval_attribution.py` 每条注入前 `shutil.copyfile(real_db, work)`
   在临时副本上写库，**不修改** `data/olist/olist.db` 原库（283 次拷贝，约 18GB I/O，
   因此**不进 CI**，需本地手工复跑）。

6. **可复现性**：全量库 63MB 未入 git；fresh clone 只含 `data/sample/olist_sample.db`，
   此时 `resolve_db_path` 返回 `db_kind` 非 `full`，本评测会**明确拒绝运行**（真值依赖分段规模）。
   复现真实命中率请在本地放置/生成全量库（见 README「启动与数据」）。

7. **本轮改造后可证伪**：命中与排名来自评测侧独立 SQL 真值表
   （`tests/test_attribution_eval_truth.py` 用"只会输出注入段的假引擎"做变异测试，
   断言此时 `hit=False` 而引擎自评 `engine_hit=True`）。报告同时给出
   **引擎 delta 表 vs 真值表的一致率 100%（最大差 0.0）**，把"算得对不对"变成独立可查的一件事。
