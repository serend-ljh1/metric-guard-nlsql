# 外部公开基准评测（A）：Spider dev · world_1

> 脚本：`evaluation/eval_external_bank.py`　语义层：`config/semantic_world.yaml`
> 复现：`python evaluation/eval_external_bank.py`
> 明细：`evaluation/reports/external_bank_world_1.json`（每题的问题/gold SQL/系统 SQL/两边结果）

## 0. 一句话结论

把语义层接到**第三方定义**的语料上（Spider dev `world_1`，N=120）：**覆盖率 30/120 = 25.0%，
覆盖内执行正确率 30/30 = 100%，敢答且答错 0 条**。在语义层目标形态（单聚合问题）上覆盖率
**28/48 = 58.3%**。

分两轮：
1. **接入轮**：第一次跑出 20/23 = 87%、**3 条错答** → 修掉，错答归零（覆盖率 17.5%）；
2. **表达力轮**：扩展 `QuerySpec`（集合/比较/区间/HAVING/否定反连接）→ 覆盖率 **17.5% → 25.0%**
   （目标形态 **43.8% → 58.3%**），**错答仍然为 0**。

## 1. 为什么需要这份评测（它替换掉了什么）

此前所有"口径命中率 / 执行正确率"都来自**本项目自编**的问题集（Olist 域，问题与标签都由
实现者定义）。自编题能证明"机制在自家数据上跑得通"，**证明不了**换一个没人参与定义的域还跑得通。

必须区分两类主张：

| 主张类型 | 自编问题集是否够用 | 原因 |
|---|---|---|
| 数学/工程性质（因子分解守恒、显著性检验、追加审计、密码学） | **够用** | 可由代码与测试独立验证（334 个测试 + 变异测试） |
| **效果类**（口径覆盖率、意图识别准确率、归因是否定位到真因） | **不够用** | 度量对象就是"能不能处理别人问的问题"，问题得由别人出 |

**数据是真实的（Olist 真实电商数据）≠ 基准是外部的。** 本报告补的是后者：
问题与 gold SQL 都来自公开学术基准 Spider（Yale LILY），答案对不对由 **gold SQL 的执行结果**
裁定 —— 不是本项目说了算。

## 2. 口径诚实声明（先读这一段）

- **`world_1` 属 Spider 的 dev 集，建语义层时看过题面。** 因此 **覆盖率 25.0% 是"开发集覆盖率"，
  不是 held-out 泛化指标**，不应被引用为"泛化能力"。
- **覆盖内执行正确率不受此影响**：它比较的是"系统 SQL 的结果行集"与"gold SQL 的结果行集"
  是否完全一致（列数、行数、取值全部比对，数值按 6 位有效数字归一），
  与"是否看过题面"无关 —— 看过了也不等于答对。
- **唯一泄露路径是"我照着题面设计词表"**，影响的是覆盖率分母/分子，不影响单题判对判错。
- 要拿到真正的 held-out 数字，需要 Spider 未公开的 test gold（本机离线环境拿不到）。
  这是本报告明确的**局限**，不是可以含糊过去的地方。

## 4. 接入轮：评测发现并修掉的真实错答

第一轮跑出来是 **覆盖 23/120、覆盖内正确率 20/23 = 87.0%、错答 3 条**。
三条错答各指向一个不同的机制缺口，全部已修并补了回归测试，修完后 **wrong 从 3 → 0**。

### 4.1 拼写差异导致"过滤静默丢失"（最危险的一类）

```
题面：How much surface area do the countires in the Carribean cover together?   ← 题面自带拼写错误
gold：SELECT sum(SurfaceArea) FROM country WHERE Region = "Caribbean"   → 234423.0
系统：SELECT SUM(co.SurfaceArea) ... 无任何过滤                           → 148956306.9
```

取值匹配不上（`Carribean` ≠ `Caribbean`）→ 过滤器一个都不加 → SQL 照跑成功 → 返回**全球**总面积。
**结果数值本身没错、口径也没被改，但范围悄悄放大成了全世界，用户从结果上完全看不出来。**

修法：新增 **未知专有名词闸**（`_unknown_entity`）。把句中"首字母大写词组"拿去与已知取值域
（含词形别名）比对，全都不认识且不是句首词 → 判定"有取值没解析出来" → 拒答。
按**词组**比对是必需的：`Central Africa` 里 `Central` 单看不在词表里，按词比对会误杀正确答案。
本闸使 5 条问题转为拒答，**逐条核对无误杀**（另 4 条分别是 `Kabul`、`Beatrix` —— 都是取值域外的实体）。

### 4.2 最值词形漏网 → 答成"另一个问题的答案"

```
题面：What is the name of country that has the shortest life expectancy in Asia?
gold：SELECT Name ... ORDER BY LifeExpectancy LIMIT 1        → Afghanistan
系统：SELECT AVG(co.LifeExpectancy) ... WHERE Continent='Asia' → 67.44
```

"取最大/最小者"需要返回**实体名称**，而语义层只返回**度量值**。首轮守住了 `lowest/largest/most`，
漏了 `shortest` —— 说明"逐词枚举"这种修法本身脆弱。

修法：扩充为词形集合并**写成域配置项**（`unsupported_patterns`），因为最值词形是语言相关的。
同时补上了 `above/below`（修 4.3 的同类问题）。

### 4.3 "与均值比较"的筛选条件被忽略

```
题面：How many cities in each district have a population that is above the average population?
gold：SELECT count(*), District FROM city WHERE Population > (SELECT avg(Population) ...) GROUP BY District
系统：SELECT COUNT(*), District FROM city GROUP BY District     ← 少了 WHERE，答成"每个辖区的城市总数"
```

修法：比较类词形进守卫。**注意这轮扩展后 `above/below` 归入"核心比较守卫"并改为条件触发**
（有数字可消费则答，无数字则拒答）——见第 5 节。

### 4.4 另外两个由评测暴露、在机制层修掉的问题

| # | 问题 | 影响 | 修法 |
|---|---|---|---|
| 5 | 同一段文字同时是两个词表的取值：world 库里 **`Caribbean` 既是地区名、又是一种语言名**，取值排序让 `ftype` 参与比较 → 按字母序选中 `language` | 一个**本该答对**的问题变成拒答（"国土总面积不支持 language 过滤"） | 取值域之间按**配置声明顺序**决定优先级（序号参与排序），显式可解释 |
| 6 | 为支持"事实表消歧"引入的按支持度换指标**过度生效** | Olist 回归：`每单件数按订单状态` 从"正确拒答"变成**静默改答成"商品件数按订单状态"** —— 用户问 A 得到 B，指标识别率表面仍 100%，口径已经漂了 | 消歧**只允许在命中词同长的真并列候选之间**发生；长度不同意味着用户用词更具体，不许顶替 |

第 6 条尤其值得记下来：它是"为了修外部基准的问题而在自家域引入回归"，靠
`eval_product.py` 的对比发现（语义层命中率 84.9%→86.4% 的"提升"其实是口径漂移）。
**"指标识别准确率"这类聚合指标看不出这种错**，必须逐条对比结果。

## 5. 表达力轮：把"拒答"变成"能答"（`QuerySpec` 扩展）

第一轮的结论是"覆盖率受限于规格表达力"。这一轮去扩规格，而不是放宽判据闸。
**新增能力全部走配置，0 行业务代码**：

| 能力 | 规格形态 | 配置声明 | 拿回的外部题 |
|---|---|---|---|
| 集合（或） | `filters=[("continent", ["Asia","Europe"])]` | 取值域 `multi: or` + 模板 `{op}` + `filter_ops.in` | [25] [26] |
| 数值比较 | `filters=[("indep_year", {"op":"lt","value":1930})]` | `numeric_filters.indep_year.cues.lt` | [69] |
| 区间 | `{"op":"between","value":[a,b]}` | `filter_ops.*.between` | （语料中此类为明细查询） |
| 否定 / 排除 | `filters=[("language_excl", "English")]` | `negated_filters`（模板 = 自包含反连接子查询） | [63] [64] [65] [66] |
| 组内筛选 | `having=[("gte", 3)]` | `having_filters.metric.cues` + `entity_dim` | [91] [92] |

**安全模型没有放松**（这是本次扩展最关键的约束）：

1. **算子不走 spec，走白名单**：规格里只出现算子**名**（`lt`/`in`/`between`…），
   SQL 记号必须来自配置 `filter_ops`/`metric_ops`。未声明的算子 → 编译期拒绝。
   实测把 `op` 写成 `"1=1 OR 1=1 --"` 或 `"'; DROP TABLE singer; --"` 一律被拒（有测试）。
2. **取值仍走字面量转义**：换算子不等于换安全模型，`ne` 的值同样逐字转义（有测试）。
3. **模板不含 `{op}` 时不允许比较算子**：否则运算符无处安放，会被静默丢弃。
4. **子查询过滤模板**（否定形态）必须是配置写的自包含 SQL；其内部别名被识别为"模板自带"，
   **不再要求注入 JOIN**（此前会误报"无法为维度/过滤注入所需表别名"）。
5. **表达能力与守卫联动**：原来"否定/比较/年份区间一律拒答"的核心守卫改为
   **条件触发 —— 命中的线索没有被成功表达成过滤条件时才拒答**。
   否则扩了能力仍被旧守卫拦住，等于白做；反过来，表达不了时**照旧拒答**，不猜。

这一轮里评测又抓出 3 个"扩展引入的新缺陷"，都已修并补测试：

| 缺陷 | 表现 | 修法 |
|---|---|---|
| `multi` 声明被取值解析器吃掉 | 配置写了 `multi: or` 仍一律拒答 | 解析结果带出 `filter_multi` |
| `at least N` 被当成最值词（argmax）→ 误拦 | "at least 3 languages" 本该可答却被拒 | 最值词表移除 `least` |
| `at least 3` 映射成 `> 3`（**off-by-one**） | 会漏掉恰好等于 3 的组，结果看起来合理 | 单独声明 `gte: ["at least"]` |

另外把两件事**明确做成拒答**（而不是含糊过去）：

- **跨指标 HAVING**："每个政体的总人口，其中平均寿命 > 72" —— 分组后要筛的是平均寿命、
  返回的却是总人口。单指标规格表达不了，若按"对本指标做 HAVING"编译会筛选错位 → 拒答（2 条）。
- **`language` 的多取值**：一个国家有多条语言行，"English and Dutch" 是**两者都会**（与语义）。
  用 IN 会答成"会其中一种"，是一个数值看着合理的错答 → 配置声明 `multi: and` → 拒答（6 条）。

## 6. 覆盖率的边界在哪里（20 条目标形态为何仍拒答）

- 12 条含取最大者（"which language is the most popular"）/交集（"both English and Dutch"）；
- 5 条同类型多取值且是「与」语义（语言）；
- 2 条取值域外实体（`Kabul`、`Beatrix`）；
- 1 条拼写差异（`Carribean`）。

**想再往上走，唯一正当路径是继续扩表达力**（EXISTS/INTERSECT、子查询比较、投影），
而不是放宽判据闸。其中"任意列投影 / 取最大者返回实体"我**明确不做**：
那会把系统变成通用查询构建器，稀释"口径治理"这条主线（42 条无聚合问题里绝大多数属此类）。

## 7. 配置化程度（换域只改 YAML，不改代码）

新增 1 个 YAML + 0 行硬编码业务逻辑：

| 配置项 | 作用 |
|---|---|
| `metrics` / `dimensions` / `filter_templates` | 15 个指标 / 6 个维度 / 10 类过滤 |
| `filter_ops` / `metric_ops` | **算子白名单**（过滤算子、HAVING 算子） |
| `matcher_keywords.metrics/dimensions/derived/grains` | **整体替换**内置中文词表 → 英文语料不必改代码 |
| `filter_values: {column: "表.列"}` | 过滤**取值域**建层时从数仓列取 DISTINCT（7 类 2130 个取值），不手抄字典 |
| `filter_values.*.aliases` | 词形别名（`Africa` ← `African`）；不加会**静默丢过滤** |
| `filter_values.*.multi` | 多取值语义：`or`（同一行只有一个取值）可表达为 IN，否则拒答 |
| `numeric_filters` / `having_filters` | 行级比较（WHERE）与组内筛选（HAVING）的线索词 |
| `negated_filters` | 否定形态：把"不…"映射到独立的反连接过滤类型 |
| `unsupported_patterns` | 域特有的超纲句式（最值/交集词形） |

## 8. 这份证据**不能**证明什么

- **不能**证明泛化能力。world_1 是 dev 集，建层时看过题面（见第 2 节）。
- **不能**证明"通用 NL2SQL 能力"。这是**指标层**：58.3% 的目标形态覆盖率衡量的是
  "配置能覆盖多少种问法"，不是 SQL 生成能力。
- **不能**证明多域可扩展性。只验证了 2 个域（Olist + world_1）。换域成本低的证据是
  "1 个 YAML + 0 行业务代码"，不是"任意域都能低成本接入"。
- **不能**证明 LLM 路径的表现。本次全部离线运行（`llm=None`），走确定性关键词路径；
  线上有 LLM 时的意图识别质量未在此评测（LLM 路径另有口径确认门兜底）。
- 单库单域（3 张表）；120 题中 65 个不同查询，**有效样本量是 65**，不是 120。

## 9. 后续工作（按性价比排序）

1. **继续扩表达力**：EXISTS/INTERSECT（"两者都会"）、子查询比较（"大于任何亚洲国家"）、
   多度量（一次返回两个指标）。这三类占了剩余拒答的大部分，且都是"口径内可认证"的扩展。
2. **接 BIRD / Spider 其它库**：验证"换域只改 YAML"在多库上的实际成本。
3. **LLM 路径对照**：同一批题在有 LLM 时跑一遍，报"确定性路径 vs LLM 路径"的覆盖率与错答率对照。
4. **拼写/别名自动发现**：`unknown_entity` 目前只报告"这个值我不认识"，
   可以进一步给出"最接近的已登记取值"（编辑距离）供人一键登记，把拒答转成可修复项。
